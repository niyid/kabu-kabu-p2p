XMRWallet as a Case Study
📅 May 2026 · ✍ Oyeniyi Dada · 🔗 github.com/niyid/xmrwallet · ⏱ 18 min read

A forensic comparison of the original XMRWallet codebase and its niyid fork, situated against the backdrop of Bisq's most recent trade protocol exploit — including a previously underreported implication for Haveno and RetoSwap — and what it all tells us about AI-assisted development in security-critical open source software.

§ 01 — Context

The Bisq Exploit — Why This Matters for Monero

What Happened on May 1, 2026

On May 1, 2026, Bisq — the long-standing, privacy-focused peer-to-peer Bitcoin trading platform — disclosed a trade protocol exploit that allowed an attacker to drain a portion of available offers. The impact was confined to open offers actively taken by the attacker over approximately twelve hours. Confirmed losses stand at approximately 11 BTC. Funds held in users' own Bitcoin wallets were not affected; Bisq maintains no central custodial pool.

As an emergency mitigation, the Bisq team set the required trading version to 2.0.0 — a version that does not exist — which blocked further exploitation by preventing v1 client connections. Bisq 2, running the Bisq Easy protocol on a completely separate codebase, was not affected.

📋
Official Statement

Bisq's preliminary investigation attributed the exploit to a missing validation check in the trade protocol, exploited using a modified client. Users with trades initiated on or after the morning of May 1 were advised to open mediation by selecting the trade and pressing Ctrl+O.

The Follow-Up: Reimbursement and Recovery

Following the exploit disclosure on X, Bisq published follow-up posts confirming a shift from emergency containment toward reimbursement planning and hotfix development. Open trades could still be completed normally; mediation and arbitration remained functional.

Because Bisq is governed through a decentralised autonomous organisation, any compensation plan must pass through community governance. Affected users cannot expect an immediate payout — the process depends entirely on treasury availability and community consensus.

History Rhymes: The 2020 Precedent

This incident mirrors the 2020 Bisq exploit almost structurally. In April 2020, the Bisq software failed to verify that a trade's payout address was the correct Bisq donation address before signing and sending the time-locked payout transaction. An attacker posing as a seller simply waited for the hard time limit to expire — the funds, the buyer's payment, and the security deposit were all redirected to the attacker's wallet. That incident resulted in approximately 3 BTC and 4,000 XMR stolen from seven users — roughly $250,000 at then-current prices. The only market affected was XMR/BTC.

In plain words, this exploit was the result of a flaw in the way Bisq trades are carried out, not in the way funds are stored.

— Bisq Network, April 2020 Security Statement

Both exploits share a common failure mode: not cryptographic weakness, but missing validation logic in application code. This distinction matters enormously for the analysis that follows.

§ 02 — Background

What is XMRWallet?

XMRWallet — also known as Monerujo — is the primary open-source Android wallet for Monero. It is non-custodial, mobile-first, and communicates directly with the Monero network via remote nodes. The application is architecturally divided into two layers:

  • Java/Kotlin Android layer: handles UI, wallet lifecycle, node management, transaction display, and user preferences.
  • Native C++ JNI layer: wraps the official Monero C++ wallet library (wallet2_api.h), providing cryptographic operations, transaction building, key management, and blockchain interaction.

This hybrid architecture is necessary because the Monero reference implementation is in C++. However, the JNI boundary is historically fertile ground for security vulnerabilities: memory management errors, null pointer dereferences, unhandled exceptions crossing language boundaries, and threading races can all cause crashes or — more dangerously — silent data corruption.

§ 03 — Context

AI-Assisted Development — The Context

AI-assisted development in security-critical open source projects manifests in several concrete forms:

Pattern 01

Systematic Refactoring at Scale

Applying a hardening pattern consistently across dozens of call sites in a large C++ file — the kind of exhaustive, mechanical work where human developers routinely miss edge cases.

Pattern 02

RAII Pattern Generation

Modern AI assistants are trained on idiomatic C++ and can generate correct resource-management wrappers that encode safety into the type system.

Pattern 03

Thread-Safety Analysis

Identifying shared mutable state and suggesting mutex-guarded access patterns.

Pattern 04

Build Tooling & Documentation

Reducing the friction of onboarding contributors and reproducing builds — itself a security property, since reproducible builds reduce supply chain risk.

The niyid fork of XMRWallet presents a compelling real-world specimen of this dynamic. The changes introduced bear the hallmarks of AI-guided refactoring: uniform pattern application, consistent defensive programming, and documentation scaffolding produced with a completeness that is difficult to sustain through manual effort alone.

The JNI Layer — Where It Really Matters

The most significant divergence lives in monerujo.cpp — the C++ bridge between Android and the Monero library. This is the most security-sensitive file in the entire application: it handles private key material, passwords, mnemonics, and raw transaction data.

JNI String Handling

In the original m2049r codebase, JNI string parameters are handled with the standard but fragile raw pattern:

monerujo.cpp — m2049r (original)C++
const char *_password = env->GetStringUTFChars(password, nullptr); // ... use _password ... env->ReleaseStringUTFChars(password, _password);

This pattern has well-known failure modes. If any exception is thrown or an early return executed between acquisition and release, the string is never freed — a memory leak. If GetStringUTFChars itself fails due to a pending exception, the resulting null pointer is used unchecked. In a wallet handling private key material, a crash at a sensitive moment could leave the wallet in a partially initialised or corrupted state.

The niyid fork replaces this wholesale with a RAII JNIStringGuard class:

monerujo.cpp — niyid (fork)C++
class JNIStringGuard { JNIEnv* env; jstring jstr; const char* cstr; bool released; public: JNIStringGuard(JNIEnv* e, jstring s) : env(e), jstr(s), cstr(nullptr), released(false) { if (s != nullptr && env != nullptr) { try { cstr = env->GetStringUTFChars(s, nullptr); } catch (...) { LOGE("EXCEPTION in GetStringUTFChars"); cstr = nullptr; } } } ~JNIStringGuard() { if (cstr && env) env->ReleaseStringUTFChars(jstr, cstr); } const char* get() const { return cstr; } bool isValid() const { return cstr != nullptr; } // Non-copyable — prevents double-release JNIStringGuard(const JNIStringGuard&) = delete; JNIStringGuard& operator=(const JNIStringGuard&) = delete; };

This is a substantive improvement. The destructor guarantees release regardless of how the scope exits. The isValid() check is explicit. Non-copyable semantics prevent double-release. The constructor catches JNI exceptions that would otherwise propagate silently into the wallet core.

Null Parameter Validation

The fork adds explicit null guard blocks at the entry of every JNI function:

monerujo.cpp — niyid (fork)C++
if (path == nullptr || password == nullptr || language == nullptr) { LOGE("createWalletJ: null parameter(s) received"); return 0; }

With 331 null/exception-related occurrences versus 98 in the original (a 238% increase), the fork has systematically hardened every JNI entry point. For a wallet application, this matters: a null JNI string that bypasses validation can result in a segmentation fault, corrupted wallet state, or — in a worst-case scenario — a write to an attacker-controlled memory location.

Threading and Mutex Usage

Both codebases use a _listenerMutex to protect the WalletListener callback. The fork adds two additional mutexes: a g_walletMutex protecting wallet creation and access paths, and a g_walletTrackerMutex guarding a global map of live wallet pointers and their creation context. This tracker enables lifecycle auditing and leak detection during development:

monerujo.cpp — niyid (fork)C++
static std::unordered_map<Monero::Wallet*, std::string> g_walletTracker; static std::mutex g_walletTrackerMutex;

The g_walletMutex reduces the risk of race conditions during concurrent wallet operations — a real concern in a mobile app where background sync threads and UI-driven operations interleave continuously.

Java Layer Changes

At the Java layer, the differences are minimal but worth noting.

The single most structurally significant change is the promotion of TransactionHistory.refresh() from private to public. In the original, refresh() is an internal detail, called only through refreshWithNotes(), which also loads user annotations. Making it public allows callers to refresh the transaction list while bypassing the notes-loading step — potentially useful for performance, but a mild encapsulation regression that risks presenting stale note data if callers aren't careful. Without accompanying documentation, this change is ambiguous in intent.

The only other Java difference is a trailing newline added to UserNotes.java — cosmetic, no functional impact.

Build System and Developer Experience

The fork adds substantial developer infrastructure:

  • BUILD_INSTRUCTIONS.md, CHECKLIST.md, QUICK_START.md: step-by-step Docker-based build guides for arm32, arm64, and x86_64 architectures.
  • build-android-arm32.sh, build-android-arm64.sh, build-android-x86_64.sh, build-all-architectures.sh: standalone architecture-specific build scripts.
  • prepare.sh: organises build outputs into the directory structure expected by CMake.
  • CONTRIBUTORS.md: structured contributor table with GitHub avatars.

The original's Makefile targets Docker builds but requires more manual intervention. The fork's build infrastructure meaningfully lowers the barrier to contribution and to reproducible builds — and reproducible builds are a security property, reducing supply chain risk.

Concerns That Need Addressing

⚠
Debug logging in production

The extensive LOGD output in JNIStringGuard and throughout the JNI layer should be conditionally compiled out in release builds. Android's logcat is accessible to other apps with READ_LOGS permission on older API levels.

⚠
Public refresh() exposure

If intentional, this requires a Javadoc comment explaining the invariants callers must maintain. If not intentional, it should be reverted. In its current undocumented state it is an encapsulation risk.

⚠
Global wallet tracker overhead

The g_walletTracker map and its mutex add runtime overhead to every wallet creation and deletion. This should be guarded by a preprocessor flag and compiled out of release builds.

⚠
extern "C" block restructuring

The fork restructures the JNI symbol export declarations. This should be verified to ensure all JNI symbol exports resolve correctly across all ABIs.

⚠
Consistent isValid() usage

A review pass to verify all JNIStringGuard call sites call isValid() before calling get() is warranted.

§ 06 — Analysis

The AI Fingerprint

The nature and distribution of changes in the niyid fork are strongly suggestive of AI-assisted development. Several characteristics support this:

  • Pattern consistency at scale: JNIStringGuard is applied uniformly across dozens of call sites. Manual refactoring of this consistency, at this breadth, is atypical without tooling support.
  • Documentation completeness: Four documentation files covering every facet of the build process have the structured completeness of LLM output.
  • Exhaustive null checking: Null guards at every JNI entry point, without exception — exactly where human developers routinely leave gaps, and where AI tools excel.
  • RAII class sophistication: Non-copyable semantics, an exception handler in the constructor, and a validity flag all reflect awareness of C++ best practices that a well-trained code assistant would naturally include.

AI assistance is not a substitute for expert review. It is a force multiplier — enabling a small team to apply best-practice patterns at a scale and speed that would otherwise require a much larger team or far more time.

The concerns identified above — verbose logging in production, the refresh() visibility change, tracker overhead — are precisely the class of issue that AI tools introduce or overlook. They reflect a lack of deployment context, not a lack of C++ knowledge. Human expert review remains the non-negotiable final stage.

§ 08 — Wider Implication

The Haveno Implication — A Fork Inherits More Than Features

There is a dimension to the May 2026 Bisq exploit that has received almost no public attention: if the vulnerability existed in Bisq v1's trade protocol, the same flaw very likely exists in Haveno — and by extension in RetoSwap, which is itself a fork of Haveno.

Understanding the Lineage

Haveno is a direct fork of Bisq, built by the Monero community specifically to replace Bitcoin with Monero as the base currency for peer-to-peer trading. RetoSwap is in turn a fork of Haveno, and currently operates the only live Haveno network with real trading. The codebase inheritance is not philosophical — it is literal. Haveno forked Bisq's Java application code, retained its P2P networking layer, kept its dispute resolution architecture, and adapted the trade protocol logic to accommodate Monero's multisignature scheme.

This means that any protocol-level vulnerability in Bisq v1's trade logic — specifically in the validation of trade messages, offer parameters, or payout conditions — is a candidate to exist verbatim in Haveno's codebase, unless that specific code path was deliberately rewritten during the fork.

Where the Protocols Diverge

The most significant architectural difference between Bisq v1 and Haveno is their multisig model. When Bisq released v1.2 in late 2019, it migrated from its original 2-of-3 multisig (with an arbitrator holding the third key) to a 2-of-2 model with no arbitrator key — a deliberate trust-minimisation move. Haveno went the other direction: it deliberately retained the older 2-of-3 multisig scheme, with an arbitrator holding the third key, because Monero's protocol constraints make the time-locked payout mechanism used by Bisq v1's 2-of-2 scheme impractical. Monero has no native timelock and no chained transaction capability in the same form Bitcoin has.

Protocol
Design
Bisq v1 (current)
2-of-2 multisig — buyer + seller only. No arbitrator key. Deadlock resolution via time-locked payout to a DAO donation address.
Haveno / RetoSwap
2-of-3 multisig — buyer + seller + arbitrator. Arbitrator holds the third key and can co-sign a payout with either party to resolve disputes.

This is a structurally important difference — but it does not insulate Haveno from the class of vulnerability that struck Bisq v1 in May 2026. The May 2026 exploit was attributed to a missing validation check in the trade protocol, exploited through a modified client. That kind of application-logic gap does not depend on whether the underlying multisig is 2-of-2 or 2-of-3. It depends on whether the receiving peer validates the parameters of incoming trade messages before acting on them.

The Shared Codebase Risk

Haveno explicitly describes itself as a fork of Bisq that shares some of its strengths, including its P2P architecture and censorship resistance. That shared heritage cuts both ways. The trade protocol message handling, the offer validation logic, and the peer communication layer in Haveno trace their ancestry directly to Bisq v1's Java implementation. Unless the Haveno team has conducted a comprehensive independent audit of these code paths — and there is no public record of one covering the specific validation gap identified in the May 2026 incident — the probability that a parallel vulnerability exists in Haveno is significant.

Haveno's arbitrator model actually extends the attack surface in one respect: because arbitrators hold a live key in the 2-of-3 multisig, a validation bypass that allows a malicious client to manipulate payout conditions could potentially enlist an arbitrator's key in an unauthorised fund release — an outcome that is structurally impossible in Bisq v1's keyless arbitrator model.

🚨
Risk Assessment

Haveno and RetoSwap users are advised to treat this as an open question until the Haveno development team issues an explicit statement confirming they have audited the specific validation gap identified in the Bisq v1 May 2026 exploit and verified it does not exist in their codebase. In the absence of such a statement, treating Haveno / RetoSwap as potentially vulnerable is the conservative and prudent position.

A Precedent Already Exists

This concern is not speculative. Haveno has a documented history of finding Bisq vulnerabilities through its own analysis and responsible disclosure. In 2021, the Haveno team identified and disclosed a vulnerability in Bisq that had allowed malicious actors to harvest payment information — bank account numbers, names, and potentially home addresses of Bisq users — at essentially no cost to the attacker. Haveno reported it to Bisq, Bisq patched it in v1.7.0, and both teams disclosed publicly. The fact that Haveno found that vulnerability in Bisq's code implies the Haveno team was studying Bisq's codebase carefully. The inverse must also be true: vulnerabilities in Bisq's protocol-handling code are candidates for existence in Haveno, because the code that was studied and forked was the code that contained those bugs.

What the May 2026 incident adds is urgency. The Haveno / RetoSwap network handles real Monero trades. The Monero privacy model means that stolen XMR is far harder to trace or recover than Bitcoin. A successful exploit of a Haveno validation gap would be, in practice, irrecoverable for victims.

§ 09 — Lessons

Lessons for AI-Assisted Development in Crypto Wallet Engineering

  • AI tools are most valuable for systematic refactoring. The JNIStringGuard transformation is the ideal AI task: apply a well-understood pattern consistently across a large, repetitive codebase. Manually refactoring 30+ JNI functions by hand is tedious, error-prone, and unlikely to be prioritised in a volunteer open-source project.
  • AI-generated code still needs expert review. The refresh() visibility change and the debug logging in production paths are exactly the class of subtle issue that requires human domain expertise to catch. AI tools do not understand deployment context the way an experienced security engineer does.
  • Documentation is a high-leverage AI use case. Build infrastructure improvements reduce the barrier to contribution and enable reproducible builds. Both are security properties.
  • Bisq's exploit history is a reminder that validation logic is where wallets and protocols fail. Whether a missing payout address check (2020) or a missing trade validation check (2026), these failures are not in cryptography — they are in application logic. AI tools that can analyse control flow and flag missing validation branches have direct security value here.
  • The JNI boundary is a persistent risk. Any project wrapping a C++ cryptographic library in Java via JNI inherits the full complexity of two memory models, two exception systems, and cross-language thread semantics. Investing in that boundary pays security dividends disproportionate to the effort.
§ 10 — Detailed Review

Detailed Code Review — File-by-File Analysis

What follows is a systematic, file-level forensic review of every meaningful difference between the upstream m2049r codebase and the niyid fork. Files are grouped by layer and ordered by security relevance.

monerujo.cpp — The JNI Bridge (1,755 → 2,814 lines, +60%)

This is the single most consequential file in the entire application. It is the C++ bridge between the Android runtime and the Monero wallet library, and it handles private keys, mnemonics, passwords, transaction data, and wallet lifecycle. Every line added here matters.

1. Global Variable Scope Regression

The upstream declares all JNI class references as static, giving them translation-unit scope — correct practice for JNI globals that should not be visible outside the compilation unit:

monerujo.cpp — m2049r (correct)C++
static JavaVM *cachedJVM; static jclass class_ArrayList; static jclass class_WalletListener; static jclass class_CoinsInfo; // present in upstream
monerujo.cpp — niyid (scope widened)C++
jclass class_ArrayList = nullptr; // external linkage — visible to linker jclass class_WalletListener = nullptr; // external linkage — visible to linker static JavaVM *cachedJVM = nullptr; // only cachedJVM retains static
⚠
Security Issue — Linkage Widening

Removing static from these JNI class references gives them external linkage — visible to other shared libraries loaded into the same process. In an Android app where multiple native libraries coexist, another library could in theory resolve and manipulate these class references if it knows the symbol names. This is precisely the kind of subtle linkage change that AI-assisted refactoring introduces when optimising for readability without full compiler-linkage awareness.

2. CoinsInfo Removal

The upstream includes class_CoinsInfo — a JNI global reference to com.m2049r.xmrwallet.model.CoinsInfo — and its initialisation in JNI_OnLoad, along with newCoinsInfo() and coinsInfoArrayList(). The fork removes class_CoinsInfo from global declarations and its initialisation in JNI_OnLoad, but retains the CoinsInfo Java class in the Android layer unchanged.

This creates a latent inconsistency. The Java class CoinsInfo remains in the Java codebase, but the native layer no longer initialises a reference to it. Any code path that calls into the native layer expecting coin control data will encounter a null class reference and crash at runtime. The fork has not yet updated the Java callers or removed the dead class — indicating this feature was disabled mid-refactor.

3. SidekickService Removal

The upstream contains a complete Sidekick integration — a hardware-wallet companion app protocol — with a functional ConfirmTransfers() that calls through to Android via JNI. The fork stubs it to auto-confirm:

monerujo.cpp — niyid (fork)C++
bool ConfirmTransfers(const char *transfers) { LOGD("ConfirmTransfers: auto-confirming (Sidekick disabled)"); return true; }

The fork has deliberately disabled Sidekick integration; the remove_sidekick.sh script documents this decision explicitly. The fork targets environments where the Sidekick hardware companion is unavailable or unsupported.

🚨
Risk: Auto-Confirmation Bypass

In the upstream, ConfirmTransfers() is a security gate — a user must physically confirm the transaction on the Sidekick device before it proceeds. In the fork, this gate is removed entirely. Any user who relied on Sidekick confirmation as a second factor for transaction signing has that protection silently eliminated. The fork must not be used in Sidekick-dependent environments without understanding this change.

4. WalletListener: struct → class with public/private Discipline

A subtle but meaningful C++ semantic change — using class with explicit private and public sections prevents accidental external access to jlistener (which holds a reference to the Java listener object), enforces the intended interface, and is more expressive of intent than the upstream's all-public struct.

5. JNI_OnUnload — Global Reference Cleanup

The upstream contains no JNI_OnUnload implementation, so global class references are leaked on unload. In practice Android's JNI layer handles this at process death, but clean teardown is a correctness requirement for library reuse. The fork adds a complete JNI_OnUnload that deletes every global reference and nulls the pointers — eliminating global reference leaks and preventing use-after-free during error recovery or test teardown.

6. Double Semicolon Defects Corrected

The upstream contains three statement-level double semicolons — harmless in C++, but indicative of copy-paste inconsistency. All three are corrected in the fork. Not a security issue, but their presence in the original suggests areas of the code that received less careful review.

7. Forward Declarations Added

The fork adds a complete set of forward declarations for all helper functions at the top of the file, replacing the upstream's reliance on definition order. This makes the file structure more maintainable and lets the compiler flag mismatched signatures at declaration time rather than at the call site.

TransactionHistory.java — Visibility Regression

A single change, one word, with outsized implications:

TransactionHistory.java — line 71Java
// m2049r (upstream) private void refresh() { ... } // niyid (fork) public void refresh() { ... }

refresh() is the raw native call to repopulate the transaction list from the Monero library. In the upstream, it is always called via refreshWithNotes(), which first invokes refresh() and then loads the user's private notes from local storage. Making refresh() public creates a call path that repopulates the transaction list without also loading notes — any caller taking this path will render a UI that shows transactions without their associated annotations, silently presenting incomplete data.

There is a plausible rationale: a performance optimisation for cases where notes are not needed. But without a Javadoc comment explaining this invariant and without any updated callers in the fork that actually use the new visibility, this change reads as unintentional — a classic consequence of AI-assisted refactoring that changes access modifiers to satisfy compilation without understanding the invariants the original visibility was protecting.

UserNotes.java — Cosmetic

A trailing newline was added to the end of the file. No functional impact.

CMakeLists.txt — Build System Restructuring

The fork makes two changes to the CMake build definition. First, it moves include_directories() before add_library() — the more conventional and robust arrangement. Second, and more significantly, it restructures the external library paths from the upstream's flat per-ABI layout to a normalised output/<abi>/lib/ structure, eliminating the monero/ subdirectory distinction. The two build systems are now incompatible: prebuilt libraries for the upstream will not satisfy the fork's CMake paths, and vice versa.

The fork also adds extensive include_directories() entries for multiple candidate header locations — a defensive, if inelegant, approach to handle variation in where the Monero headers are placed by different build environments.

Dockerfiles — Pinned vs. Rolling Base Images

The upstream uses debian:stable — a rolling tag that resolves to whatever Debian calls "stable" at build time, meaning builds on different days may use different Debian versions and creating irreproducibility. The fork pins to debian:bullseye across all three Dockerfiles (arm32, arm64, and a new x86_64 image), ensuring every build from the same Dockerfile produces an identical environment. Pinned base images are a supply chain security best practice, at the cost of needing manual updates when Bullseye reaches end-of-life. The fork also adds androidx64.Dockerfile, enabling emulator testing and x86_64 device support — purely additive, with no security implications.

.gitignore — Developer Hygiene Overhaul

The upstream's .gitignore is minimal (16 lines). The fork's is comprehensive (91 lines), covering build artifacts, NDK outputs, IDE files, log files, and external library directories — including rules for *.a and *.so, which prevent precompiled native libraries from being committed. Binary blobs in version control cannot be audited by reviewers and create supply chain risk; the upstream has no such rule.

check_libs.sh deserves specific attention. A arm64-v8a library with the wrong machine type would silently fail to load at runtime or, worse, load with incorrect alignment assumptions — this script catches exactly that class of error. It is the kind of validation tool that is straightforward to generate with AI assistance but that many projects omit entirely.

The niyid fork makes meaningful security improvements — the JNIStringGuard pattern, systematic null guards, JNI_OnUnload cleanup, and double semicolon corrections are all correctness wins. The pinned Docker base images and check_libs.sh improve supply chain integrity.

However, the fork carries three material concerns that require resolution before production use: the linkage widening on JNI class globals, the verbose diagnostic logging that must be compiled out of release builds, and the incomplete CoinsInfo removal. The Sidekick auto-confirm is intentional but must be documented as a deployment constraint.

The fork is not a drop-in replacement for the upstream. It is a development branch with a partially completed refactor. Upstreaming the JNI hardening selectively — while retaining Sidekick support and CoinsInfo — would produce the strongest combined codebase.

⌗ Conclusion

Where This Leaves Us

XMRWallet sits at a meaningful intersection: privacy-sensitive software, built on a complex dual-language architecture, maintained by volunteers, and used by people for whom operational security is not abstract. The Bisq exploits of 2020 and 2026 are a constant reminder that the cost of missing validation or incomplete hardening in this ecosystem is measured in real funds stolen from real people.

The Haveno implication compounds this. The Monero ecosystem's primary P2P trading infrastructure — Bisq for BTC pairs, Haveno and RetoSwap for XMR-native trading — shares a common codebase ancestry. A protocol-level vulnerability discovered in one is a candidate to exist in the others. The privacy properties of Monero that make these platforms attractive are the same properties that make fund recovery after an exploit essentially impossible. The stakes of getting the validation logic right are correspondingly higher.

The niyid fork of XMRWallet demonstrates what AI-assisted development can look like when applied with intention: systematic pattern application, comprehensive build documentation, and meaningfully improved defensive programming — all at a velocity and consistency that is difficult to sustain through manual effort alone.

AI will not write perfectly secure cryptocurrency wallet software. But it can help a small, skilled team do significantly better work — and in the Monero ecosystem, where privacy and security are foundational, better work directly translates to safer outcomes for users. The question the Bisq and Haveno communities now face is whether the same AI-assisted rigour can be brought to bear on trade protocol validation logic before the next exploit, rather than after it.
